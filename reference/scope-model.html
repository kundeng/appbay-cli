Scope Model Reference

Namespace and Collection – complete reference

Overview

Appbay has two organizational concepts. Each controls a different aspect of how apps are grouped, configured, and deployed.

Concept Controls Compose mapping Cardinality
Namespace Deployment identity and variable scope Container, network and edge-fragment names Single per app
Collection App selection Which docker compose up calls are made Multi per app

Collection is NOT part of variable resolution — it is a selector only.

Importantproject: and environment: were replaced by namespace:

RFC-001 §4 collapsed the two scope fields into one. As of v0.0.1-alpha.12:

# check-docs-manifests: ignore
# appbay.yaml -- before
project: homelab
environment: prod

# appbay.yaml -- now
namespace: homelab.prod

A namespace is flat and dot-delimited. Values shared across namespaces live one level up in the installation config, not in a hierarchy of names.

A non-default project: or environment: is now a parse ERROR, not a silently ignored key — the manifest fails with a message naming namespace:. The literal value default is still accepted, because it carried no information and every shipped manifest used it.

⚠️ environment: inside a service is Docker Compose’s own field and is untouched. Only the top-level scope field is gone.

WarningOnly ${{project.DOMAIN}} actually resolves today

The ${{scope.KEY}} reference vocabulary is unchanged by the rename — it is still project, environment and service. That asymmetry is deliberate and permanent, not a migration still owed: namespace: and ${{project.KEY}} are different things that shared a word.

  • namespace: is a per-app label. It disambiguates container names, network aliases and state keys. It has no variable store and never had one.
  • ${{project.KEY}} reads the installation config — one file per host, shared by every app on it, whatever their namespaces.

Renaming the prefix to ${{namespace.KEY}} would point every reference at a scope that holds nothing. The two are independent, so the §4 field rename does not oblige a reference rename.

What the docs below describe as three variable stores is currently one, and it holds one key. loadProjectVars reads a single domain: line out of $APPBAY_HOME/etc/system.yaml and returns { DOMAIN }. The exposed keys are an allow-list, not everything in the file: home:, project: and container_runtime: live there too and are deliberately not variables — home: in particular is an absolute path, which is machine state and not something a manifest should be able to interpolate. Nothing reads projects/<name>/project.yaml or environments/<env>.yaml, so ${{environment.KEY}} and ${{service.KEY}} resolve against empty maps and always fail.

A reference to an unknown key survives the render as a literal and the deploy then refuses the app, so this fails safe — but no error names the missing store directly.

Namespace

A namespace is a deployment identity. It distinguishes two instances of the same app in one installation, and it scopes the variables an app resolves against.

# appbay.yaml
namespace: uom.sim

Absence means “decided at deploy time”. The field is optional and has no default, which is what lets a value supplied at compile time take effect — a schema default would shadow it.

What it controls

  • Container names: appbay.<namespace>.<app>.<service>
  • The app’s private network: <namespace>_<app>_internal
  • The shared-network alias other apps dial: <namespace>_<app>_<service>
  • The generated edge fragment: <namespace>.<app>.caddy / .yml

⚠️ Dots become hyphens wherever the namespace reaches a hostname. A dot separates labels in DNS, so uom.sim_litellm_web would parse as host uom in domain sim_litellm_web and resolve to nothing. An app in namespace uom.sim publishes uom-sim_litellm_web.

An un-namespaced app is unchanged

When namespace: is absent — the case for every shipped manifest — the namespace is omitted from all four names entirely:

no namespace namespace: uom.sim
container appbay.litellm.web appbay.uom-sim.litellm.web
network litellm_internal uom-sim_litellm_internal
alias litellm_web uom-sim_litellm_web
edge fragment litellm.caddy uom-sim.litellm.caddy

This is deliberate: including it unconditionally would rename every container on every existing host in order to disambiguate installations that have nothing to disambiguate.

When to use a namespace

  • Two instances of one app in one installation (uom.sim and uom.prod)
  • Separate variable values for the same config keys

Collection

A collection is an operational grouping – a named set of apps that are deployed, restarted, or stopped together. Collections are purely a selection mechanism.

# appbay.yaml
collection: [ai-stack, gpu-apps]

What it controls

Which apps are included in a batch operation. Nothing else.

What it does NOT control

  • Variable values (use environment for that)
  • Naming prefixes (use project for that)
  • Network isolation (use project for that)

Multi-valued

An app can belong to multiple collections:

# ollama
collection: [ai-stack, gpu-apps]

# jellyfin
collection: [media, gpu-apps]

CLI usage

appbay up --collection ai-stack          # Deploy all ai-stack apps
appbay up ollama webui                   # Deploy specific apps (no collection needed)
appbay down ollama webui tts             # Stop apps by name
appbay restart ollama jellyfin           # Restart apps by name

Variable resolution

Variables are resolved by scope prefix — each ${{scope.KEY}} reference targets exactly one variable store. There is no cascading fallthrough.

Collection is NOT part of variable resolution. It is a selector, not a scope level.

Variable reference syntax

Syntax Resolves from Only from
${{project.KEY}} etc/system.yaml (domain: only) project store only
${{environment.KEY}} etc/projects/<name>/environments/<env>.yaml environment store only
${{service.KEY}} Service-level vars in appbay.yaml or .env service store only

Undefined variable references produce explicit errors with the scope and key name. Appbay never silently substitutes empty strings.

Resolution example

# projects/homelab/project.yaml
vars:
  DOMAIN: home.lan
  TZ: UTC

# projects/homelab/environments/prod.yaml
vars:
  DOMAIN: homelab.example.com    # separate environment-scope value, does NOT override project-scope
  TZ: America/New_York

Resolution of ${{project.DOMAIN}} in any environment: - Returns home.lan — resolved from project.yaml only

Resolution of ${{environment.DOMAIN}}: - In prod: returns homelab.example.com — resolved from prod.yaml - In dev (if dev.yaml has no DOMAIN): compile error — undefined variable

Magic generators

Generator Output Persisted?
${password:N} Random N-character password Yes – stored in generated-values.yaml
${uuid} Random UUID v4 Yes
${base64:N} Random N-byte base64 string Yes
${hash} Deterministic hash of (project + env + service + key) No – always reproducible
${timestamp} Current ISO timestamp No – evaluated at render time

Generated values are keyed by (project, environment, service, var_name). Once generated, they are reused on subsequent compiles to ensure deterministic output.

Compose runtime mapping

When you run appbay up --collection ai-stack:

1. Select apps tagged with collection: ai-stack
   -> [ollama, webui, tts]

2. For each app, resolve variables:
   ${{project.DOMAIN}} from $APPBAY_HOME/etc/system.yaml
   (${{environment.KEY}} and ${{service.KEY}} resolve against empty maps -- see the
    warning at the top of this page)

3. Compile each app:
   upstream transform -> overlays -> traits -> render

4. Execute each app as a separate Compose project:
   docker compose -f renders/ollama/docker-compose.rendered.yml up -d
   docker compose -f renders/webui/docker-compose.rendered.yml up -d
   docker compose -f renders/tts/docker-compose.rendered.yml up -d

Each app is an independent Compose project. They communicate via shared networks (e.g., appbay_shared), not via Compose’s internal service discovery.

Filesystem layout

⚠️ This is the intended layout, not the built one. etc/projects/ is not read by anything — ProjectConfigSchema and EnvironmentConfigSchema exist and have no non-test consumers, and the string "projects" is never joined into a path. The one file that is read is $APPBAY_HOME/etc/system.yaml at the root.

$APPBAY_HOME/
  project.yaml                          # the ONE config that is read; `domain:` -> ${{project.DOMAIN}}
  etc/
    projects/                           # ⚠️ specified, not implemented -- nothing reads this
      homelab/
        project.yaml
        environments/
          prod.yaml
    apps/
      ollama/                           # App definition
        appbay.yaml                     # namespace: uom.sim, collection: [ai-stack]
        docker-compose.yml
      jellyfin/
        appbay.yaml                     # collection: [media]
        docker-compose.yml

Reserved keys vs tags

Type Keys Semantics
Reserved namespace, collection, operator, service Fixed meaning – drives Appbay behavior
Removed project, environment Replaced by namespace; a non-default value is a parse error
Tags Anything via tags: No fixed meaning – UI filtering and bulk ops only

Anti-patterns

Do not use collections for variable scoping

# WRONG: no collection-level variable resolution exists
# RIGHT: use a namespace, or app-level overrides
namespace: prod

Do not use a namespace for operational grouping

# WRONG -- a namespace is a deployment identity, not a label
namespace: ai-apps
namespace: media-apps

# RIGHT -- group with collections, which are multi-valued
collection: [ai-stack]    # ollama
collection: [media]       # jellyfin

Do not use a namespace to select different app sets

# WRONG -- namespace does not choose which apps deploy
namespace: minimal
namespace: full

# RIGHT -- collections select, the namespace identifies
collection: [core]
collection: [core, extras]
