Secrets Management

URI-based secret references, auto-generation, and verification
NoteThe vault password is one of three

It unlocks vault.enc and nothing else. The password you use to sign in to AppBay, and the passwords your users use to sign in to deployed apps, are separate and independently recovered — see The Three Credentials.

Overview

Appbay uses URI-based references for secrets. Instead of embedding secret values in configuration files, you reference them by URI. Secrets are resolved at deploy time and injected into the runtime environment – never written to rendered artifacts in plaintext.

This design ensures that:

  • Secrets are never committed to version control
  • Secrets are never visible in plan diffs or logs
  • Secrets can be rotated by updating the source, not by editing app configs
  • Different environments can use different secrets via the same URI patterns

URI schemes

Appbay v1 supports six URI schemes for secret references:

vault:// (default — local vault)

The local vault (AES-256-GCM encrypted KeePass .kdbx file) is Appbay’s default secrets provider. Secrets are auto-generated if missing and stored locally.

traits:
  - type: secrets
    refs:
      DB_PASSWORD: vault://prod/nextcloud/db-password
      SMTP_KEY: vault://prod/shared/smtp-api-key
      REDIS_PASS: vault://nextcloud/REDIS_PASSWORD

The URI format is vault://<path>/<KEY>: the last segment is the key, and everything before it is the path. The path may be any depth — vault://a/b/c/d/FIELD is valid and resolves FIELD under a/b/c/d.

In practice every shipped manifest uses two segments, scoped by app: all 66 vault:// references across both catalogs are vault://<app>/<KEY>, e.g. vault://photoprism/PHOTOPRISM_DB_PASSWORD. There is no environment segment — that was a documentation artefact, not a shape the parser has ever required.

The local vault provides:

  • Auto-generation of missing secrets (magic vars: ${password:32}, ${uuid}, etc.)
  • KeePass-compatible .kdbx format (viewable in KeeWeb or KeePassXC)
  • No external dependencies — runs entirely on the local filesystem

file:// (file-based secrets)

⚠️ Not permitted in appbay.yaml since RFC-001 §3.2. The provider still exists and still resolves, but a manifest may only carry vault:// references — the storage backend is an installation choice, and a manifest naming one breaks on any host that made a different choice. The example below is kept to document the URI form.

References a file on the host filesystem. The file should contain only the secret value with no trailing newline. Files should be permissions-restricted (0400 or 0600).

# check-docs-manifests: ignore
traits:
  - type: secrets
    refs:
      TLS_CERT: file:///etc/ssl/certs/homelab.pem
      TLS_KEY: file:///etc/ssl/private/homelab.key
      SSH_KEY: file:///home/appbay/.ssh/deploy_key

This is the simplest approach and requires no external service.

env:// (environment variables)

⚠️ Not permitted in appbay.yaml since RFC-001 §3.2. The provider still exists and still resolves, but a manifest may only carry vault:// references — the storage backend is an installation choice, and a manifest naming one breaks on any host that made a different choice. The example below is kept to document the URI form.

References an environment variable on the host where Appbay runs. Useful for secrets provided by CI/CD pipelines or system-level configuration.

# check-docs-manifests: ignore
traits:
  - type: secrets
    refs:
      GITHUB_TOKEN: env://GITHUB_TOKEN
      CLOUDFLARE_API_KEY: env://CF_API_KEY

The host environment variable must be set when appbay up runs. If it is not set, the deploy fails with an actionable error.

vault:// (local encrypted vault)

The built-in local vault. Zero external dependencies — an AES-256-GCM encrypted JSON file at $APPBAY_HOME/var/lib/vault.enc. Secrets are scoped by app name.

traits:
  - type: secrets
    provider: vault
    refs:
      DB_PASSWORD: vault://kestra/DB_PASSWORD
      API_KEY: vault://kestra/API_KEY

The URI format is: vault://<scope>/<key> where scope is typically the app name. Flat vault://KEY uses scope “default” (shared across apps).

Auto-generation: If a vault secret doesn’t exist on first deploy, it’s auto-generated (32-char hex by default). Add ?gen=password:24 for a different format. Subsequent deploys reuse the stored value.

# Initialize the vault (auto-generates master password)
appbay secrets init

# Manually set a secret
appbay secrets set kestra/DB_PASSWORD mypassword

# Import secrets from an app's .env file
appbay secrets import kestra

# List vault contents
appbay secrets vault

keepass:// (KeePass database)

⚠️ Not permitted in appbay.yaml since RFC-001 §3.2. The provider still exists and still resolves, but a manifest may only carry vault:// references — the storage backend is an installation choice, and a manifest naming one breaks on any host that made a different choice. The example below documents the URI form only.

References a value inside a KeePass .kdbx file via keepassxc-cli. Useful when you already manage secrets in KeePass.

# check-docs-manifests: ignore
traits:
  - type: secrets
    provider: keepass
    refs:
      DB_PASSWORD: keepass:///path/to/vault.kdbx#group/entry/Password

sops:// (encrypted files)

⚠️ Not permitted in appbay.yaml since RFC-001 §3.2. The provider still exists and still resolves, but a manifest may only carry vault:// references — the storage backend is an installation choice, and a manifest naming one breaks on any host that made a different choice. The example below documents the URI form only.

References a value inside a SOPS-encrypted file. The file is decrypted at deploy time using the host’s SOPS configuration (age, GPG, or cloud KMS).

# check-docs-manifests: ignore
traits:
  - type: secrets
    refs:
      DB_PASSWORD: sops://secrets.enc.yaml#database.password
      API_KEY: sops://secrets.enc.yaml#services.api.key

The URI format is: sops://<file-path>#<yaml-path>

SOPS-encrypted files can be safely committed to version control since they contain only encrypted values.

Trait properties

Property Type Default Description
refs record required Map of env var name to secret URI or magic generator
provider enum vault Default provider: vault, keepass, file, env, or sops. Each ref can override via its URI scheme.
injection enum runtime-env How secrets reach the container: runtime-env (process env) or wrapper (tmpfs file mount)

Declaring secrets

Secrets are declared using the secrets trait in appbay.yaml. Because the secrets trait is service-scoped, it must be declared under services.<name>.traits:

# apps/nextcloud/appbay.yaml
services:
  nextcloud:
    traits:
      - type: secrets
        refs:
          POSTGRES_PASSWORD: vault://prod/nextcloud/db-password
          NEXTCLOUD_ADMIN_PASSWORD: vault://prod/nextcloud/admin-password
          SMTP_PASSWORD: vault://nextcloud/SMTP_PASSWORD
          REDIS_PASSWORD: ${password:24}

Each key in refs becomes an environment variable injected into the service at runtime.

Auto-generation

Magic generators in refs values are evaluated once at compile time and their output is stored in the state store. Subsequent compiles reuse the stored value for deterministic output. This works with ${password:N}, ${uuid}, ${base64:N}, and ${hash}.

services:
  nextcloud:
    traits:
      - type: secrets
        refs:
          # Generates a strong 32-char password on first compile; reuses the same value after that
          REDIS_PASSWORD: ${password:32}
          INSTALL_ID: ${uuid}

For KeePass-backed secrets, auto-generation is handled by the KeePass database — create entries before the first deploy using KeeWeb or KeePassXC.

Injection modes

Secrets can be injected in two ways:

Runtime-env (default)

Secrets are resolved and passed as process environment variables to docker compose up. They exist only in the container’s runtime environment and are never written to disk.

services:
  app:
    traits:
      - type: secrets
        injection: runtime-env    # this is the default
        refs:
          DB_PASSWORD: vault://myapp/DB_PASSWORD

Wrapper-file (file-based, no env exposure)

For applications that read secrets from files (Docker-secrets-aware apps, Java apps reading /run/secrets/), the wrapper-file mode writes secrets to a shared Docker volume as files. No environment variable exposure.

services:
  app:
    traits:
      - type: secrets
        injection: wrapper-file
        refs:
          DB_PASSWORD: vault://myapp/DB_PASSWORD
          API_KEY: vault://myapp/API_KEY

At deploy time:

  1. A one-shot shepherd container writes resolved values as files to a Docker volume
  2. The target service mounts the volume read-only at /run/secrets/<app>/
  3. Each secret becomes a file: /run/secrets/myapp/DB_PASSWORD, /run/secrets/myapp/API_KEY

No env exposure: docker inspect shows zero secret environment variables — secrets exist only as files in the volume.

Entrypoint-wrapper (opt-in, highest security)

For apps that read process.env at startup, the entrypoint-wrapper mode rewrites the container’s entrypoint to run the small appbay-inject binary, which decrypts a per-app secret bundle from a mounted volume and then execs the original process. Secrets are set as shell variables via export — they inherit into the process but are not visible to docker inspect.

services:
  app:
    traits:
      - type: secrets
        injection: entrypoint-wrapper
        refs:
          DB_PASSWORD: vault://myapp/DB_PASSWORD

Trade-off: The compose file is rewritten (entrypoint + command + configs), and the container gains a dependency on the injector binary and its volume. No Appbay service needs to be running — the bundle is on disk. This is the highest-security option but breaks the “upstream compose unchanged” guarantee.

Security guarantees

Appbay enforces the following security rules for secrets:

Never in plaintext

Secret values never appear in:

  • Rendered compose files – URIs are resolved at runtime, not during compilation
  • Plan diffs – secret changes show [REDACTED] instead of values
  • Logs – both CLI and web UI redact any string matching a known secret pattern
  • SQLite cache – only secret URIs (not values) are stored in secrets_meta
  • Git diffs – since secrets are not in config files, they cannot be committed
  • SSE events – deployment status messages redact secret values

Example: redacted plan diff

  services:
    web:
      environment:
-       DB_PASSWORD: [REDACTED]
+       DB_PASSWORD: [REDACTED]
        DB_HOST: postgres-db

Even when a secret changes, the diff only shows that it changed, not what it changed to.

Scoped secrets

Secrets can differ per deployment by varying the vault path.

⚠️ The environment.yaml mechanism this section used to describe does not exist. It told you to define an ENV var in etc/projects/<name>/environments/<env>.yaml and interpolate it into the URI. Nothing reads that file — ProjectConfigSchema and EnvironmentConfigSchema have no non-test consumers, and the string "projects" is never joined into a path — so ${{environment.ENV}} resolves to nothing and the URI never substitutes.

Until a value store exists, scope secrets by writing the path you want directly, or by distinguishing them at the app level:

services:
  nextcloud:
    traits:
      - type: secrets
        refs:
          DB_PASSWORD: vault://nextcloud/DB_PASSWORD

The path is any depth you like, so a deployment that genuinely needs separate values can carry the distinction in the path itself — vault://prod/nextcloud/DB_PASSWORD and vault://dev/nextcloud/DB_PASSWORD are both valid and resolve independently. What does not work is interpolating a scope reference into the URI, because no store populates one.

Secret lifecycle

Vault secrets are authoritative for initial provisioning. Understanding when secrets are read by containers is critical for safe rotation.

Stateful services (databases)

Database containers (Postgres, MySQL, MongoDB, Redis with persistence) only read password environment variables on first initialization — when the data volume is empty. After that, the password is stored inside the database’s own data directory. Changing the vault secret after initialization has no effect on the running database.

To rotate a database password after first deploy:

  1. appbay secrets set myapp/DB_PASSWORD newpassword — updates the vault
  2. Connect to the database container and run the appropriate command:
    • Postgres: ALTER USER myuser PASSWORD 'newpassword';
    • MySQL: ALTER USER 'myuser'@'%' IDENTIFIED BY 'newpassword';
    • MongoDB: db.changeUserPassword("myuser", "newpassword")
  3. appbay up myapp — restarts the app container with the new env var

Stateless services (apps, APIs)

Application containers that read secrets from environment variables on every startup will pick up vault changes on restart. appbay up triggers a container recreation, which re-reads the environment.

Examples: API keys, JWT signing secrets, SMTP credentials, OAuth client secrets.

Rotation summary

Secret type Vault change + redeploy sufficient? Additional action needed?
App API keys Yes No
JWT/session secrets Yes (existing sessions invalidated) No
Database passwords No ALTER USER in the DB
Redis AUTH No (if persistent) CONFIG SET requirepass
TLS certificates Yes (if mounted via env) No

Best practices

Use the local vault for production. The file:// and env:// schemes are convenient for development, but the local vault provides encrypted storage, auto-generation, and KeePass-compatible management.

Run appbay secrets check before deploying. Make it part of your workflow to catch missing or misconfigured secrets before they cause deploy failures.

Use auto-generation for database passwords. Let Appbay generate strong passwords for internal services like databases and Redis. You never need to type or remember these.

Keep SOPS files in version control. Since they are encrypted, they are safe to commit. This gives you versioned, auditable secret storage without an external service.

Avoid env:// for long-lived secrets. Environment variables are visible to any process on the host. Use file:// with restricted permissions (0400) or the local vault for sensitive credentials.
