Core Concepts

Understand apps, traits, overlays, scopes, collections, and operators

The application model

Appbay is inspired by the Open Application Model (OAM) – a specification for describing cloud-native applications. OAM separates the concerns of application developers, platform operators, and infrastructure providers. Appbay adapts these ideas for single-node Docker Compose deployments.

The central idea: Docker Compose is the application model. Your docker-compose.yml file is the component definition. Appbay adds traits, scopes, and policies on top – without replacing Compose.

Apps

An app is a directory under $APPBAY_HOME/etc/apps/ containing a docker-compose.yml file. The directory name is the app name. No configuration file is needed to register an app – just create the directory.

etc/apps/
  ollama/
    docker-compose.yml       # required
    appbay.yaml              # optional -- only if you need traits, overlays, or scope
  jellyfin/
    docker-compose.yml
    appbay.yaml
  whoami/
    docker-compose.yml

An app can contain multiple Compose services. For example, a nextcloud app might have services for the web server, the database, and a Redis cache. Appbay treats the entire directory as one deployable unit.

Services

A service is a Docker Compose service within an app. Appbay does not redefine what a service is – it uses the standard Compose service model. Traits can be applied at the service level (e.g., ingress on a specific service) or at the app level (e.g., backup for the entire app).

Traits

A trait is a reusable, declarative transformation that adds or modifies behavior. Traits are attached to apps or services in appbay.yaml and are applied during compilation.

Appbay v1 ships with seven core traits:

Trait Scope Purpose
ingress service Traefik/Caddy routing, TLS, exposure modes
gpu service GPU device passthrough (Nvidia/CDI/ROCm)
auth app Caddy Security browser login and role-based authorization
hooks service Init containers, sidecars, config injection
scoped-env app Variable injection from project/environment scopes
secrets service URI-based secret resolution
backup app Scheduled backup with retention policy

Traits follow OAM rules:

  • Applied in declaration order. The order you list traits matters.
  • One configuration per trait type per service. You cannot attach two ingress traits to the same service.
  • Conflict declarations. Some traits declare conflictsWith to prevent incompatible combinations.

See Traits for detailed documentation of each trait.

Scopes

Appbay has three organizational concepts that control different aspects of the runtime:

Installation settings — $APPBAY_HOME/etc/system.yaml

Settings that describe this installation rather than any one app. Written by appbay init and read on every command.

key values default meaning
project string hostname project name for scope resolution
domain string — base domain for ingress routing
catalog_source path or git URL bundled catalog where appbay install looks
container_runtime docker | podman docker which container binary every command invokes
ingress_provider traefik | caddy traefik which reverse proxy the ingress trait emits for
edge_identity provider list one local store who the Caddy edge authenticates against
server_host hostname appbay.<domain> where the edge serves the control plane 
# $APPBAY_HOME/etc/system.yaml
project: homelab
domain: homelab.example.com
container_runtime: podman
ingress_provider: caddy

container_runtime and ingress_provider are set through appbay init, which applies them on re-init too and reports created / updated / unchanged:

appbay init --container-runtime podman --ingress-provider caddy

Both accept a per-invocation override — $APPBAY_CONTAINER_RUNTIME and $APPBAY_INGRESS_PROVIDER — which wins over the file and is not persisted.

Who the edge lets in

By default the Caddy edge has a single local identity store — the accounts appbay edge users manages, hashed into etc/apps/caddy/config/security/users.json. edge_identity: replaces that with a directory or an OIDC provider, at which point appbay stores no human password at all: what remains is one bind password or client secret, a vault:// reference like any other.

# $APPBAY_HOME/etc/system.yaml
edge_identity:
  providers:
    - type: local            # keep a break-glass local account
      realm: local
    - type: ldap
      realm: corp
      servers: ["ldaps://dc1.corp.example.com"]
      bindDn: "CN=svc-appbay,OU=Service,DC=corp,DC=example,DC=com"
      bindPasswordRef: "vault://caddy/LDAP_BIND_PASSWORD"
      searchBaseDn: "DC=corp,DC=example,DC=com"
      searchUserFilter: "(&(sAMAccountName=%s)(objectclass=user))"
      groupRoleMap:
        "CN=AppBay-Admins,OU=Groups,DC=corp,DC=example,DC=com": ["authp/admin"]

appbay init renders this into the edge’s Caddyfile and adds bindPasswordRef to caddy’s secrets trait, so the credential travels the ordinary secret path and never reaches a file on disk. Omitting the key is the single local store — byte for byte the configuration every installation has always had, so adding nothing changes nothing.

⚠️ Provider order is load-bearing. Caddy Security tries them in the order listed and the first is the portal’s default store, so a broad provider listed first shadows a narrower one after it.

⚠️ An oidc provider couples edge start-up to the IdP. Caddy Security fetches the issuer metadata and the signing keys while provisioning, so an unreachable IdP fails the whole edge rather than degrading logins. Keeping a local provider in the list is the break-glass path.

Reaching the control plane through the edge

appbay server start writes a Caddy site block for the control plane itself, so the web UI is reachable at appbay.<domain> behind the same login portal as every other app — and behind an admin-only policy, because it is the one stack that can reach the container runtime socket. Set server_host: to serve it somewhere else.

Nothing is written when the installation runs Traefik (the auth portal is Caddy Security only) or when there is no domain: and no server_host: — a local install has no name to serve it at, and that is normal rather than an error.

When that route is written, appbay server start also binds port 3000 to loopback, so the edge becomes the only way in from the network. Without a route it stays on all interfaces — closing the port when there is nowhere else to go in is a lockout, not a hardening.

install edge route port 3000
Caddy + a domain written 127.0.0.1:3000
Caddy, no domain none 0.0.0.0:3000
Traefik none 0.0.0.0:3000

APPBAY_BIND always wins, either way — APPBAY_BIND=0.0.0.0 appbay server start is the escape hatch if your edge is configured but not yet actually serving.

⚠️ The web UI still checks its own password. Handing authentication to the edge is the rest of RFC-001 §1; the loopback bind is its precondition, because with the port open on every interface, trusting an identity the edge forwards in a header would let anyone who can reach 3000 set that header themselves.

NoteTwo files used to be called project.yaml

RFC-001 §2.1 renamed the installation config to etc/system.yaml, because the two shared nothing but a name and the root one held no project-scoped keys at all.

path purpose keys
$APPBAY_HOME/etc/system.yaml this installation — the table above home, project, domain, catalog_source, container_runtime, ingress_provider, edge_identity, server_host
$APPBAY_HOME/etc/projects/<name>/project.yaml one project’s variable scope, described just below name, vars, defaults

⚠️ The old path $APPBAY_HOME/project.yaml is still READ for one release so an install that has not been re-inited keeps working; appbay init moves it. Everything from here to the end of this section is about the second file.

Project

A namespace disambiguates one copy of an app from another on the same host. It is a label, not a variable scope: it does not select a variable file, and ${{project.KEY}} does not read it. That reference resolves against the installation config above, which is one file per host shared by every namespace on it — see Scope Model.

# appbay.yaml
namespace: homelab

Container, network and shared-alias names derive from the app name and the namespace when one is declared. Without a namespace — the default — containers are appbay.<app>.<service>, volumes are prefixed <app>_, and apps join appbay_shared (or whatever shared_network specifies). With namespace: homelab, the container becomes appbay.homelab.<app>.<service> and the shared alias homelab_<app>_<service>, so two namespaces of one app do not collide.

Dots in a namespace become hyphens wherever the name reaches a hostname, because a dot separates labels in DNS: namespace: uom.sim publishes uom-sim_<app>_<service>.

Use a namespace when you need two copies of an app side by side — homelab and work-lab get distinct containers, networks and shared aliases and never collide.

⚠️ They do not get distinct variables. There is one domain: per installation, so ${{project.DOMAIN}} is the same value in every namespace. Per-namespace variables are not implemented; use a plain Compose ${VAR} from the app’s .env for a value that must differ.

Environment

An environment is a deployment variant. It determines which variable values, secret URIs, and certificate resolvers are used.

# appbay.yaml
namespace: prod

project and environment were a single axis in disguise — every shipped manifest set both to default — so RFC-001 §4 collapsed them into one dot-delimited namespace. Typical values: prod (real domain, production certs), dev (localhost, staging certs), or a compound like uom.sim.

⚠️ There is no environment: field any more. It was removed with project: in RFC-001 §4 and the schema now accepts only the literal default for either, so an old manifest still parses and a manifest trying to use one fails loudly instead of being silently ignored. Put the variant in namespace: — namespace: uom.sim — and deploy a second copy alongside the first.

Collection

A collection is an operational grouping – a named set of apps that deploy, restart, or stop together. Collections are multi-valued and purely a selection mechanism.

# appbay.yaml
collection: [ai-stack, gpu-apps]

Usage: appbay up --collection ai-stack deploys all apps tagged with that collection.

Collections do not participate in variable resolution. They are selectors, not scope levels.

Variable resolution

Variables are resolved by scope prefix. Each ${{scope.KEY}} reference targets a specific variable store:

Syntax Resolves from
${{project.KEY}} projects/<name>/project.yaml only
${{environment.KEY}} projects/<name>/environments/<env>.yaml only
${{service.KEY}} Service-level vars in appbay.yaml or .env only

There is no cascading fallthrough between stores. An undefined reference produces an explicit error naming the scope and key; Appbay never silently substitutes an empty string.

WarningOnly the project store is implemented

The table above is the intended model. Today loadProjectVars reads a single domain: line from $APPBAY_HOME/etc/system.yaml, and nothing reads projects/<name>/project.yaml or environments/<env>.yaml at all. So ${{project.DOMAIN}} is the one reference that resolves; ${{environment.KEY}} and ${{service.KEY}} always fail.

An unresolved reference survives the render as a literal and the deploy then refuses the app, so this fails safe — but plan around it rather than writing references that cannot work.

# In appbay.yaml or .env
DOMAIN: ${{project.DOMAIN}}         # the only scope reference that resolves today

Magic generators

Appbay supports generator expressions that produce values on first evaluation and are then stored for deterministic re-renders:

Generator Example Description
${password:N} ${password:16} Random alphanumeric string of length N
${uuid} ${uuid} Random UUID v4
${hash} ${hash} Deterministic hash of project + environment + service + key
${base64:N} ${base64:32} Random base64 string of N bytes
${timestamp} ${timestamp} Current timestamp (evaluated at render time, not stored)

Overlays

Conditional overlays are Compose fragments that are applied only when specified conditions are met – typically when a peer app is active. This enables declarative cross-app wiring without manual configuration.

# apps/webui/appbay.yaml
overlays:
  - when: [ollama]
    services:
      web:
        environment:
          - OLLAMA_BASE_URL=http://ollama_web:11434

When Appbay detects that ollama is in the active app set, it merges this fragment into WebUI’s rendered compose. See Conditional Overlays for full syntax.

How a deploy actually executes

There is no operator service. Whichever interface you used — CLI, web, or desktop — calls @appbay/core in its own process, which compiles your app, spawns the configured compose client, reports, and exits. Runtime capabilities (GPU availability, runtime version, disk, OS) are probed from the host during that run.

A deployed app keeps running after every Appbay process is gone. That is the design: Appbay is a deployer, not a supervisor.

In v1, there is a single operator co-located with the server. The operator field in appbay.yaml is optional and defaults to local. The architecture supports multiple operators on different nodes in future versions.

System apps

Appbay ships system apps as built-in definitions that are seeded into $APPBAY_HOME/etc/apps/ during appbay init. They include infrastructure apps and ready-to-deploy user apps:

Infrastructure apps (deployed automatically or on demand to enable Appbay features):

System app Purpose
Traefik Reverse proxy, ingress routing, TLS termination (ingress-only mode)
Caddy Integrated ingress + Caddy Security edge (authentication, authorization)
Whoami Starter demo app for verifying ingress routing

Bundled user apps (ready-to-deploy with pre-configured appbay.yaml):

System app Purpose
Ollama Local LLM inference server
Open WebUI Web UI for LLM models, integrates with Ollama
Nextcloud Self-hosted file sync and collaboration
Jellyfin Media server
Vaultwarden Bitwarden-compatible password manager
Home Assistant Home automation platform

System apps are regular Appbay apps with their own docker-compose.yml and appbay.yaml. They are authored in the system-apps/ directory of the Appbay source tree and seeded into $APPBAY_HOME/etc/apps/ during appbay init.

WarningContributors: edit the directory, run the generator

appbay init seeds from the embedded definitions in packages/core/src/system-apps.ts, not from the system-apps/ directory. The definitions are compiled into the binary so that seeding does not depend on filesystem paths relative to the source tree, which are unavailable in a bun-compiled binary.

system-apps/ is the authored source, and a generator produces the embedded file from it. The workflow is three steps:

# 1. edit the app definition
vim system-apps/caddy/config/Caddyfile
# 2. regenerate the embedded copy
node scripts/generate-system-apps.mjs
# 3. commit BOTH

packages/core/src/__tests__/system-apps-sync.test.ts fails the build if the committed generated file is not what the generator would produce right now, so a forgotten step 2 cannot reach main.

⚠️ The generated file is committed rather than built on demand, because appbay init must seed system apps from a single compiled binary with no source tree present.

NoteWhy this matters historically

Before the generator, these were two hand-maintained copies with nothing between them. They drifted to 8 differing files and 2 apps that existed only as embedded strings — and it cost the default ingress: a depends_on: [socket-proxy] left in the Traefik definition after socket-proxy was deleted, which makes Compose reject the entire project rather than skip the service.

What Appbay is and is not

Appbay is a centralized control plane for Docker Compose apps. It adds ingress routing, authentication, secret management, and lifecycle orchestration on top of standard compose files — without modifying the upstream compose.

It is not a service mesh. There are no per-app sidecar proxies, no east-west traffic interception, no mTLS between containers, and no distributed tracing injection. Cross-cutting concerns (routing, auth, secrets) are handled by shared centralized services:

  • Traefik or Caddy handles all HTTP routing and TLS termination (one instance, not one per app)
  • Caddy Security handles authentication and authorization for the Caddy edge (one instance, not one per app)
  • The secrets vault resolves secrets at deploy time and injects them via process environment or file mounts

When your app needs authentication, Appbay generates Caddy Security authorization policies and injects Remote-User/Remote-Email/Remote-Groups headers — it doesn’t inject a proxy container next to your app.

This centralized approach means deploying 30 apps doesn’t create 60 containers. Your compose files stay unmodified. Your apps start and stop independently of the control plane (in default mode).

The compiler pipeline

When you run appbay up, the compiler transforms your app definitions into runnable Compose files, then deploys them:

The pipeline runs in two phases. For each discovered app, stages run in this order:

  1. Discover – Scan etc/apps/ for directories with docker-compose.yml. Parse and validate appbay.yaml with Zod schemas. Errors are recorded but do not block other apps.
  2. Upstream transform – For apps with an upstream.source, apply namespace isolation first (internal network creation, volume prefixing, shared network aliases). This runs before variable resolution so that scope references inside the upstream compose are visible to the resolver.
  3. Resolve variables – Evaluate ${{scope.KEY}} references against the variable store named by the scope prefix. Only project has a populated store ($APPBAY_HOME/etc/system.yaml’s domain:); see the warning under Variable resolution. Magic generators (${password:N}, ${uuid}, etc.) are evaluated and persisted.
  4. Select overlays – Evaluate when clauses against the active app set; merge matching fragments into the compose model.
  5. Apply traits – Transform the compose model (add Traefik config, GPU devices, auth middleware, etc.) in declaration order.
  6. Render – Write final compose YAML to var/lib/renders/<app>/
  7. Plan/Diff – Compare rendered output against the previous render on disk; produce a redacted diff.

After compilation, docker compose up -d is invoked with the rendered artifacts. The compile phase is deterministic: the same inputs always produce the same rendered output.
